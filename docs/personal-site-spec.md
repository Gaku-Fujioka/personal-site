### 見た目と寸法の初期目安

- 白系を基調に、青を少量使用。すっきりしているが冷たすぎない。
- 本文は日本語の読みやすいゴシック系。system-uiと日本語フォールバックで開始し、外部フォント必須にしない。
- 本文約16px、行高1.7〜1.8。Homeの英語名はPC約40px、モバイル約30〜32pxを目安に調整する。
- コンテンツ最大幅は約1040px。PCの左右余白は32px以上、モバイルは20px程度。
- ヘッダー下に中央配置のプロフィール。写真枠はPC約128px、モバイル約96px。
- 自己紹介本文は横に長くしすぎず、最大幅約640px。
- セクション間はPC約64px、モバイル約40pxを目安とする。
- ボタンは丸みのある細い枠、作品画像は角丸12〜16px。大きな影や過度なグラデーションは避ける。
- 小さな星、見出しの短い青線、リンクの矢印で遊び心を出す。
- 飾りは本文の読みやすさを妨げない。星や矢印が装飾なら支援技術から隠す。
- 合意済み：初版の動きはCSSのみ。小さな星は静的に置き、見出しの青線、リンクの色・下線、矢印の小さな移動で表現する。
- 推奨仕様：ホバー・フォーカス時の変化は約120〜180ms、矢印の移動は2px程度。常時動く装飾、強いズーム、視差スクロールは使わない。`prefers-reduced-motion` では移動を止め、色・下線・フォーカス枠で状態を伝える。
- View Transitions APIとHTML-in-Canvas APIは使用しない。3D実験の削除については第17節を参照。
- 上記の寸法は実装用の目安。内容量と画面幅に応じて調整する。

### レスポンシブ

- モバイルから設計。320px幅でも横スクロールや文字切れを起こさない。
- Home：写真→英語名→日本語名→肩書き→自己紹介→外部リンク→Aboutリンクの順。
- SNSリンクは横並び、必要に応じて折り返す。
- 作品はPC2列、モバイル1列。例えば768px付近で切り替えるが、内容に基づいて調整してよい。
- 写真は正方形を円に切り抜く。作品のサムネイル枠は16:9を基本にそろえる。
- AboutとProjectsの長文は左揃え。Homeのプロフィール以外まで中央揃えにしない。

## 9. Journal・記事管理

### 合意済みの使い方

- PCのブラウザにある入力欄で記事を書く。普段の投稿で、ローカルファイル編集やGitコマンドを必須にしない。
- 数行の備忘録と、見出し・写真を含む長いイベント記録・旅行記の両方を書けるようにする。技術記事の主な投稿先はQiita。
- 記事管理はDecap CMS。下書き保存 → 見た目の確認 → 公開を分ける。
- サイトのソースコードはGitHubで公開する。下書き・未公開写真・プレビューは自分だけが閲覧できる状態にする。
- 記事一覧は文章中心、写真は任意の小さなサムネイル。新しい順に並べ、タグ絞り込みを初版から備える。
- 写真は本文の途中に、短い説明を添えて配置する。写真だけのアルバムや末尾の専用ギャラリーは初版では作らない。

### 一覧・本文・タグ（推奨仕様、承認済み）

- `/journal/` の見出しは「Journal」、説明は「日々のメモと、出かけた記録。」。タイトル・投稿日・概要・タグを縦並びのリストで見せる。写真がある項目だけ右側等に小さく配置する。
- スマホも1列。写真が本文幅を圧迫する場合は文章の下に移し、写真の有無で空白の枠を残さない。タイトルの長い日本語を複数行で読めるようにする。
- 一覧の並びは投稿日が新しい順。同日はslug順等の一定の順序にする。更新日を変更しただけでHomeの最新2件や一覧の先頭へ移動させない。
- タグは「すべて」と、公開記事で使用中のタグをリンクで表示する。初期の選択肢は「備忘録（memo）」「イベント（events）」「旅行（travel）」、1記事に複数選択可。タグなし記事は「すべて」に載せる。語彙の追加は設定で行い、表記の揺れを避ける。
- 絞り込みは `/journal/tags/[tag]/` への通常のリンクで実現し、JavaScriptなしでも利用可能にする。選択タグを文字・下線・現在地の属性で示し、「すべて」へ戻れるようにする。各項目からタグを押しても同じ一覧へ移動する。
- 存在しないタグや記事は404。公開記事が0件の場合、タグ操作は表示せず「Journalを準備中です。」と表示する。記事の代わりに架空の旅行記・イベント参加記録を作らない。
- 本文ページは、Journalへ戻る導線 → 記事タイトル（h1）→ 投稿日・更新日・タグ → 概要 → 任意のカバー写真 → 本文 → Journalへ戻る導線。カバーがなければその領域を省く。
- 本文は最大約680px、PC・スマホとも左揃えの1列。本文約16px、行高1.8を目安にする。h2・h3、段落、箇条書き、引用、リンク、写真と説明を初版で扱う。
- 本文の目次、前後記事、関連記事、読了時間、いいね、コメント、予約公開、キーワード検索、ページ分割、RSSは後回し。記事が増えた時点で必要性を見直す。

### 記事データ（推奨仕様、承認済み）

Decap CMSのフォームに次の項目を用意し、1記事をMarkdown本文と先頭の設定情報として保存する。通常の更新でMarkdown記法を直接入力することは必須にせず、編集ボタンで見出し・リスト・リンク・画像を追加できるようにする。

| 項目 | 必須・既定値 | 用途 |
| --- | --- | --- |
| title | 必須 | 記事名。カード・h1・共有タイトルに利用 |
| slug | 作成時に設定し、公開後は固定 | 短い半角英数字・ハイフンのURL識別子。重複不可。タイトル変更でURLを変えない |
| publishedAt | 公開時に必須 | 投稿日。入力の初期値は当日、公開前に本人が確認。日付は日本時間の暦日として扱う |
| updatedAt | 任意 | 内容を更新したときだけ指定。投稿日と異なる場合に表示。保存のたびに自動変更しない |
| description | 任意 | 一覧・Home・共有の概要。目安40〜120字。未入力なら本文冒頭から装飾を除いた短い文章を作る |
| tags | 任意、空配列 | 定義済み候補から複数選択。初版は備忘録・イベント・旅行 |
| cover | 任意 | カバー兼一覧用写真。未設定なら画像領域を省く |
| coverAlt / coverCaption | coverがある場合は説明を入力 | 画像の内容を伝えるaltと、表示する短い補足 |
| body | 公開時に必須 | 短文・長文を許容。生のHTMLやスクリプトを執筆者に書かせる運用はしない |
| 写真ごとのalt・caption | 本文写真がある場合 | altは視覚情報、captionは場所・場面等の短い説明。両方を入力できるフォームを用意 |
| 編集状態 | CMSの管理情報 | 下書き・確認・公開を管理。公開状態を本文の手入力と二重管理しない |

未来日の予約公開は実装しない。公開対象の日付・画像参照・必須情報に不整合があれば、確認時またはビルド時に明確なエラーにして修正する。時刻の推測、参加日と投稿日の混同はしない。

### 非公開の保存先と公開反映（推奨の構成）

- 公開ソースリポジトリには、表示用コード・CMSの秘密情報を含まない設定・共通画像を置く。
- 別の本人用の非公開GitHubリポジトリに、記事と写真を保存する。リポジトリ名・接続情報は未設定で、勝手に作成しない。
- Decapの編集フローを使い、未公開の編集は非公開リポジトリの作業ブランチ、公開を確定したものは公開用ブランチで管理する。「非公開リポジトリ内の公開用ブランチ」であり、GitHub上で記事ファイルを一般公開する意味ではない。
- 通常の保存・公開操作は、将来の運用時には記事側のコミット等として記録される。この仕様相談中にコミットを行う許可を意味しない。
- 公開時のビルドだけが、秘密情報を用いて公開用ブランチの確定済み記事を取得する。参照される公開済み画像のみを取り込み、AstroのContent Collections等で検証・静的生成する。
- 下書きブランチ、未公開画像、記事の取得用トークンを、公開リポジトリ、`public/`、配信するJavaScript、生成HTML、公開ビルド成果物に混ぜない。URLを隠す、noindexを付ける、一覧に載せないだけでは非公開要件を満たさない。
- 初版のプレビューはログイン後のCMS編集画面内で行う。本人用ブラウザで取得した下書きを表示し、外部から開ける下書きページや公開プレビューURLは作らない。本文の書体・余白・画像を公開記事と揃え、PC幅とスマホ幅を確認できるようにする。
- 公開確定後にサイトの再生成を自動で開始し、成功後に表示を更新する。反映まで待ち時間があることと、成功・失敗の確認場所を運用手順に書く。失敗時は以前の公開サイトを維持し、失敗を記事0件として隠さない。
- 管理画面のGitHubログイン、非公開データの取得、公開反映の連携には認証設定等が必要。具体的な認証の置き場所とビルド連携は、公開サービス決定後に確定する。無料枠の条件を確認し、不要な独自認証・データベースを作らない。

### 本人が記事を増やす手順

1. PCのブラウザで本人用管理画面を開き、GitHubでログインする。
2. 新規記事を作り、タイトル・URL識別子・日付を設定し、必要に応じて概要・タグ・カバーを入力する。
3. 本文を書き、必要な位置へ写真を追加してaltと短い説明を入力する。
4. 下書き保存する。保存・再ログインで続きから編集でき、一般公開には反映されない。既に公開した記事を下書き編集する場合も、公開を確定するまでは前の公開内容を保つ。
5. 管理画面のプレビューでPC・スマホの読みやすさ、写真の説明、投稿日、リンクを確認する。
6. 公開を確定し、サイトの生成・反映結果を確認する。公開した記事がHomeの最新2件、Journal一覧、タグ一覧へ反映されることを確認する。
7. 訂正時は既存記事を編集・確認・公開する。更新日を必要に応じて指定し、slugは維持する。

CMSの初回設定、GitHub接続、写真と記事の保存先、再生成の連携は初期構築作業としてまとめる。普段の記事更新で同じ設定を繰り返させない。READMEに初回設定と日々の投稿手順を分けて残す。

### ローカル確認と本番連携の区別

- 外部接続前でも、記事0件のHome・Journal・タグなし状態を実装・確認できる。ローカル専用の記事保存先を用意する場合は公開コードの管理対象から除外する。
- テスト用の記事・画像を使う場合は「表示確認用」と明示し、公開用の実績・体験談として残さない。納品用の通常ビルドは、本人が提供した公開記事か0件のいずれかにする。
- ローカルのCMS動作とプレビュー、公開記事の表示・生成は、外部サービスの未接続と区別して確認する。GitHub本番ログイン・非公開保存・公開反映の実動作は接続設定後に別途確認し、未接続のまま完了扱いにしない。

## 10. 未提供の素材とリンク・画像の扱い

- 顔写真は本人が公開を希望しているが、まだ提供されていない。初版は青い円のGを仮表示。架空人物の写真や参考サイトの人物写真を使わない。
- 作品画像は未提供。Homeの生成画像から作品画面を切り抜いて実績として使わない。
- 作品画像は、家・地図などの簡単な図形と作品名による仮サムネイルを用意し、「画像準備中」と明示する。実在UIを捏造しない。重い画像生成や外部素材検索は不要。
- GitHub / Qiita / XのプロフィールURLは未提供。ユーザー名を推測してリンクしない。
- URLが未設定ならサービス名＋「準備中」を非リンクの表示にする。`href="#"`、空href、偽のクリック動作は不可。
- Qiita未設定時は「Qiitaでの発信を準備中」と表示し、壊れたボタンを置かない。
- 実データは1か所に集める。例えばprofileデータ、projects配列を用意し、URLがnullならリンクを描画しない構成とする。
- 本人の写真・作品画像・URLに差し替えるファイルとフィールドをREADMEに記載する。
- 正式な公開ドメインも未設定。canonical、OG URL、サイトマップに架空ドメインを入れない。公開先確定後の設定手順を残す。
- Journalの記事・旅行やイベント写真は未提供。0件で初版を成立させ、公開用の文章をAIの架空体験で埋めない。

### 画像の差し替え・表示（推奨仕様）

- プロフィールと作品は、既存の `src/data/profile.ts` の `photo`、`src/data/projects.ts` の各 `image` を差し替え窓口とする。実画像のsrc・alt・width・heightをまとめて指定できる構成を活かす。
- プロフィールはPC約128px・スマホ約96pxの円形、作品サムネイルは16:9。人物や作品の大事な部分が切れないよう、切り抜きの位置も確認する。
- Journal写真はCMSから追加する。本文は元の縦横比を保ち、本文幅以内で表示する。カバーと一覧用サムネイルは16:9を目安に切り抜く。写真を大きく表示する専用ビューアーは初版では作らない。
- 公開する写真の幅・高さを出力に指定する。本文より下の画像は遅延読み込みを基本にし、画面幅に応じた画像サイズを配信する。
- Astro標準の画像処理等を活用し、公開用のコピーをWebP等の適切な形式・解像度に最適化する。元写真を上書きせず、写真の差し替えや記事更新後のビルドで反映する。外部の画像管理サービスは初版では追加しない。
- 最適化対象はAstroが処理できる保存先へ取り込むか、ビルド時に変換する。`public/` に置いただけの元画像を、最適化済みとは扱わない。後の実装時に最終的な差し替え先をREADMEへ記載する。
- 顔写真・作品画像がない場合は指定の仮表示。Journalのカバーがない場合は画像枠を省く。壊れた画像参照は検証で検出し、「画像準備中」で実画像の取得失敗を隠さない。

## 11. 共通の操作・アクセシビリティ・メタデータ

- `html lang="ja"`、viewport、UTF-8を設定。
- 各ページに固有のtitle・description。例：`Gaku Fujioka | 藤岡楽空のポートフォリオ`。
- titleとh1は区別し、ページの主題をh1、区分をh2、必要な下位項目をh3にする。
- header / nav / main / footerを適切に使う。本文へ移動するスキップリンクを設ける。
- ナビ・リンクはキーボードで操作でき、focus-visibleで位置が明確に分かる。
- リンクや選択中状態を色だけで表さない。下線・ラベルなどを併用。
- 本文のコントラスト比4.5:1以上を目安に確認。補助文字、タグ、ホバー状態にも注意する。
- 淡い区切り線は装飾用。操作対象の識別に線だけが必要な場合は十分なコントラストを確保する。
- 顔写真・作品画像には用途に合うaltを付ける。装飾画像は空alt。Gの仮表示は本人写真であると説明しない。
- タップ領域は可能な限り44px程度を確保する。
- 画像差し替え時に幅・高さを指定し、レイアウトの飛びを減らす。
- SEOのためという理由で特定色が順位を上げる等の説明をサイト内に入れない。
- タグはリンク、CMSの保存・公開はボタンとして扱い、キーボードで選択・実行できるようにする。タグの折り返し、長い記事タイトル、写真なし、記事0件でも読み順と操作順を保つ。
- 外部リンクは同じタブで開く。通常の戻る操作と、読む人が自分で別タブを選ぶ操作を妨げない。クリック時だけ働く偽のリンクは使わない。
- 日付には `time` と機械可読の日付を使う。記事本文にh1を重複させず、記事タイトルをh1、本文をh2以下で構成する。

### ファビコン（合意済み：GF、詳細は推奨仕様）

- Gaku Fujiokaの「GF」を組み合わせる。淡い青の角丸四角と青い文字を基本にし、16px程度でも判別できる単純な形にする。
- SVGを基本にし、必要なPNGの代替画像も用意する。プロフィール写真の仮アイコン「G」とは用途を分ける。ファビコンのGFを理由にプロフィールの仮表示を変える必要はない。
- 現在の `public/gaku.svg` はGのため、後の実装時にGF版へ変更する。今回の仕様相談では変更しない。

### 404（推奨仕様）

- 共通ヘッダー・フッター、白系背景と青、小さな静的な星を使う。大きな「404」、h1「ページが見つかりませんでした。」を表示。
- 説明文は「URLが変更されたか、ページが存在しない可能性があります。」。
- 「Homeへ戻る」と「Journalを見る」を正常なリンクとして置く。自動転送はせず、読み手が移動先を選べるようにする。
- ローカルと公開環境の両方で、存在しない記事・タグも含め404を返すことを確認する。

### SNS共有・ページ情報

- 合意済み：全ページで共通の共有画像を使う。Journalにカバーがあっても、共有画像は共通とする。記事ごとの画像生成や専用画像の入力欄は初版では作らない。
- 推奨仕様：白系背景に青いアクセント、GF、Gaku Fujioka、藤岡楽空を配置した1200×630pxのPNG。架空の写真や作品画面を含めない。
- 各ページで固有のtitle・descriptionを持つ。Journal記事は「記事タイトル | Journal | Gaku Fujioka」、説明はdescriptionまたは本文から作った概要を使用する。記事0件でもJournal自体の説明は設定する。
- OGPのtitle・description・image、共有カードの情報を整える。記事は `og:type="article"`、通常のページはwebsiteを使用する。画像の説明も設定する。
- 公開URLが決まってからcanonical・`og:url`・共有画像の絶対URLと必要な公開設定を入れる。未確定の段階で架空ドメインを入れない。
- 下書き・管理画面・404を公開記事の一覧やサイトマップに載せない。管理画面のnoindexは補助であり、下書き非公開の代わりにはしない。
